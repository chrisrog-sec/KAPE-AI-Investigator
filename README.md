## Recovering interrupted ingestion

The `recover_checkpoints.py` helper reconstructs `reports/events_normalized.json` from completed per-file ingestion checkpoints. It is intended for situations where ingestion was interrupted or the normalized event output needs to be recovered without unnecessarily processing every source file again.

### How it works

The recovery helper:

- Checks that each checkpoint's source file exists under the selected evidence directory.
- Calculates the source file's SHA-256 hash and compares it with the checkpoint.
- Validates record source paths and hash provenance.
- Reconstructs the normalized event output using the schema expected by the current project code.
- Creates a timestamped backup of an existing output before replacing it.
- Reports skipped checkpoints and records.

The helper does not modify the original evidence files or checkpoint files. It does not need to make API calls.

### Prerequisites

Before running recovery, make sure you have:

- Python installed.
- The project files available locally.
- The original KAPE evidence directory.
- Completed checkpoint files from a previous ingestion run.
- Any dependencies required by the project scripts.

### Required project structure

Run the helper from the project root. The relevant files and directories should look like this:

```text
KAPE-AI-Investigator/
├── recover_checkpoints.py
├── test_recover_checkpoints.py
├── requirements.txt
└── reports/
    ├── .ingestion_checkpoints/
    │   └── [existing checkpoint files]
    └── events_normalized.json
```

The normalized output file may not exist yet. It is shown above because it is the expected recovery destination.

The evidence directory is separate from the project:

```text
E:\
└── KAPE-Output-2\
    └── [original KAPE evidence files]
```

These paths are examples based on a Windows setup. Your evidence directory may be located elsewhere.

**Important:** Do not create empty checkpoint files and expect recovery to reconstruct data from them. Use checkpoints generated by a previous ingestion run. Do not delete or move existing checkpoints before recovery.

### Step 1: Open the project directory

Open PowerShell and change to the project root:

```powershell
cd "C:\Users\Chris\KAPE-AI-Investigator"
```

Replace the example path with the location where you cloned or saved the project.

### Step 2: Activate the virtual environment

If you use the project's virtual environment, activate it:

```powershell
.\.venv\Scripts\Activate.ps1
```

If you do not use a virtual environment, ensure Python and the required dependencies are installed in your active Python environment.

If dependencies have not yet been installed, you can install those listed in `requirements.txt`:

```powershell
python -m pip install -r requirements.txt
```

### Step 3: Check your evidence and checkpoint paths

Confirm that the original evidence directory exists and contains the source files referenced by the checkpoints.

The default example uses:

- Evidence source: `E:\KAPE-Output-2`
- Checkpoints: `reports\.ingestion_checkpoints`
- Recovered output: `reports\events_normalized.json`

Replace the evidence path with your own location. The checkpoint directory should contain checkpoints from your previous ingestion run.

Close any running ingestion or investigation processes before recovery. Keep a copy of the project folder where practical.

### Step 4: Run the recovery helper

From the project root, run:

```powershell
python .\recover_checkpoints.py --source "E:\KAPE-Output-2" --checkpoints ".\reports\.ingestion_checkpoints" --output ".\reports\events_normalized.json"
```

Change the `--source` value if your evidence directory is elsewhere.

The command uses these arguments:

| Argument | Purpose |
|---|---|
| `--source` | Root directory containing the original evidence files |
| `--checkpoints` | Directory containing existing ingestion checkpoints |
| `--output` | Destination for the reconstructed normalized event file |

### Step 5: Review the recovery results

Review the helper's console output to see which checkpoints and records were accepted or skipped.

Expected behaviour:

- **Valid checkpoints found:** eligible records are reconstructed into the normalized output.
- **Some checkpoints rejected:** the helper reports skipped checkpoints or records.
- **No valid checkpoints found:** the existing output is left unchanged.

If recovery does not produce the expected output, verify the evidence path, checkpoint directory, source-file hashes, and checkpoint compatibility before trying again.

Do not delete checkpoints simply because some were rejected. Investigate the reported reason first.

### Step 6: Run the tests

From the project root, run:

```powershell
python -m unittest .\test_recover_checkpoints.py -v
```

The tests use synthetic temporary evidence and do not make API calls.

A successful test run should report that the tests passed. If a test fails, review the failure output before relying on the recovery helper.

### Safety and limitations

- Keep the original evidence unchanged.
- Do not edit or delete checkpoint files as part of routine recovery.
- Back up the project before replacing important generated output.
- Recovery relies on the checkpoint format and schema expected by the current code.
- A matching SHA-256 hash supports source-file integrity verification, but does not independently prove that the evidence or checkpoint contents are trustworthy.
- Only checkpoints that pass the helper's validation checks should be eligible for recovery.
- Do not share real forensic evidence, recovered event data, investigation reports, or sensitive case details in a public repository.

**Note:** This guide describes the intended workflow. Directory creation, error handling, and command-line behaviour should be verified against the current implementation of `recover_checkpoints.py` before relying on those details.
